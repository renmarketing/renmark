# ADR-001 — Role-Based Governed Orchestration for Renmark

**Numbering note:** this ADR lives in the `.bootstrap-renmark/decisions/` namespace, which is intentionally separate from `.renmark/memory/decisions.md`'s own ADR-001..ADR-045 sequence, per `governing-bootstrap-directive.md` §4 ("do not place bootstrap governance artifacts inside `.renmark/` until the new canonical artifact system is implemented and verified"). There are therefore two documents both titled "ADR-001" in this repo, in two deliberately isolated locations — this is not a numbering error. If/when this ADR migrates into `.renmark/memory/decisions.md` (per addendum-01 §"Transition Gate 1"), it will be renumbered into that sequence (next available: ADR-046).

**Date:** 2026-08-01
**Status:** Proposed — part of release R-0.0 ("Baseline and PRD Reconciliation"), work package WP-2. Not yet ACCEPTED in the release-lifecycle sense (`governing-methodology-addendum-02.md`'s 10-state ladder) — that happens at R-0.0's own acceptance step, which evaluates this ADR alongside the rest of R-0.0's evidence package.
**Supersedes:** nothing in `.renmark/memory/decisions.md`'s ADR sequence. Extends/refines the architecture proposed in `governing-architecture-roadmap.md` (2026-07-31) as revised by `governing-methodology-addendum-01.md`, `-02.md`, and `-03.md` (2026-07-31 to 2026-08-01).

## Context

Renmark's orchestration had grown expensive: agent calls could reinterpret the project, replan settled decisions, load excessive history, dispatch unnecessary subagents, or overengineer small changes — sometimes spending more inference managing the workflow than implementing the feature (see `governing-architecture-roadmap.md` §1 for the original problem statement).

A read-only audit of the current system (`current-system-audit.md`, produced 2026-07-31 by 5 parallel Explore subagents covering command entrypoints, dispatch/execution/routing, context/memory/PRD-planning, verification/retry, and artifact schemas/tests/analytics) found that Renmark already has substantial primitives that a naive from-scratch redesign would have duplicated: `SubagentInput`/`SubagentOutput` (schema-enforced, `IsolationViolation` on breach) already function as a Work-Order/Work-Result contract; `pipeline.json` vs `lifecycle.json` are already separated the way a Milestone-Contract/runtime-state split would want; `program_driver.py`'s structured-signal-only stop evaluation already partially enforces "no unsupported success claims"; `delivery_state.py`'s hard byte-budget-with-error is an existing precedent for enforced artifact limits. The audit's biggest gap finding: **no unified ledger** (6+ siloed append-only logs today) and **no role/authority enforcement layer** (dispatch gating exists, but nothing checks whether a dispatched role is permitted to do what it's attempting).

A first proposed roadmap (`governing-architecture-roadmap.md`) specified a 10-role hierarchy, a 10-milestone sequence gated by internal task completion, and deferred UX/compatibility protection to Milestone 8. The Owner's review (`governing-methodology-addendum-01.md`) identified two structural problems with that proposal: (1) a "role zoo" risk — treating the role model as a requirement that every role be a separate persistent agent, rather than an authority-boundary model that can be implemented mostly as deterministic code; (2) protecting the existing vibe-coder UX cannot wait until milestone 8 — it must be established at the start. A second review (`governing-methodology-addendum-02.md`) identified a further problem: even the corrected Phase 0–8 sequence still measured completion as "a phase's internal tasks are done," not "a user can use, evaluate, and accept a meaningful new capability" — reproducing the same category of problem one level down.

## Decision

Adopt the following architecture for Renmark's own orchestration, and — per new PRD requirements REQ-26/REQ-27 (`PRD.md`, 2026-08-01 revision) — as the standard methodology Renmark applies to every project it plans, implements, verifies, and releases:

1. **Four runtime roles, not ten.** General Contractor (the active Claude Code/Codex session — controls workflow, communicates with the Owner), Planner (Architecture mode for major system decisions, Milestone mode for executable release work — modes of one role, not separate mandatory agents), Worker (implements bounded scope, cannot redesign/replan/dispatch agents), Inspector (verifies independently, cannot repair — repairs become separate Work Orders). Governor, Integrator, and Ledger are primarily deterministic software components, not conversational agents. (`governing-methodology-addendum-01.md` §3, reconciliation table.)

2. **Authority boundaries, enforced regardless of whether a step is a separate model call.** Every dispatch needs a reason, bounded scope, defined output, call budget, retry limit, and stopping condition. Nested dispatch, speculative agents, unlimited repair loops, and automatic replanning are prohibited; replanning requires evidence (an Owner requirement change, an impossible contract, or a genuine architectural conflict).

3. **Release-oriented completion, not task-oriented completion.** The unit of "done" is a **release** — a distinct, user-testable capability that passes a 4-level acceptance ladder (component verification → system verification → user acceptance → release observation) and a 10-state lifecycle (PLANNED → READY → IN DEVELOPMENT → INTEGRATED → ENGINEERING VERIFIED → RELEASE CANDIDATE → USER ACCEPTANCE → RELEASED → OBSERVED → CLOSED) — not merely "a Worker's tasks are implemented and tests pass." A Phase (the internal sequencing/dependency container) may not close on internal task completion alone. (`governing-methodology-addendum-02.md`, `-03.md` Part 2.)

4. **Three (four) execution paths, classified before dispatch.** Patch (bounded correction, no material new user journey — Work Order → integration → tests → applicable inspection → patch release, skipping full planning ceremony). Feature release (distinct new user capability — milestone contract → implementation → integration → engineering verification → user acceptance → release). Architectural release (subsystem/boundary/data-model/compatibility change — architecture planning → Owner gate → milestone planning → implementation → migration+integration testing → user acceptance → controlled release). Research spike (bounded experiment → evidence, never silently becomes implementation).

5. **UX and compatibility protection at the front, not the end.** The single-command entry point (`/renmark:start` et al.) and existing approval-gate surfaces (PRD REQ-4, REQ-12, REQ-18) remain the only required points of user interaction by default. Internal governance complexity — role names, per-handoff approvals, governance artifacts — is invisible by default and may only become visible when doing so measurably reduces user effort, inference cost, or failure rate (PRD REQ-26, codified 2026-08-01 as part of this same release's WP-1).

6. **Owner remains the default final acceptance authority** for user-visible feature releases, architectural releases, changes to Renmark's own governance/orchestration behavior, and releases materially affecting cost/context/routing/reliability — even when scenario *execution* is delegated. Delegation must be explicit per release contract, never assumed. (`governing-methodology-addendum-03.md` Part 2, Decision 2.)

7. **Sequencing stays incremental and gated.** Phase 0 (PRD reconciliation + measurable baseline) gates Phase 1 (UX/compatibility harness) + the blocking subset of Phase 2 (authority/budget controls), which together are expected to become the first user-testable release. No future phase's release is broken down into a contract until the preceding blocking release reaches CLOSED, not merely ENGINEERING VERIFIED. Only one blocking release is actively worked at a time.

8. **WritingMate integration is explicitly deferred** behind bounded Work Orders, structured Worker responses, scope validation, secret redaction, safe patch integration, local test execution, independent inspection, and provider budgets/failure controls — unchanged from the original roadmap's sequencing intent, now expressed as a later phase/release rather than Milestone 10.

## Migration and rollback

This ADR describes a target architecture arrived at through three rounds of Owner review; it does not itself implement any of it. Implementation proceeds one release at a time, starting with R-0.0 (this ADR is R-0.0/WP-2). Each release change is additive and gated: `.bootstrap-renmark/` stays isolated from `.renmark/` until a release's artifacts pass migration inspection (per `governing-bootstrap-directive.md` §4, §11 Transition Gates). No production code (`renmark/**`, `plugin/**`) has been modified as of this ADR's authorship — R-0.0's own contract explicitly prohibits it except for a narrowly-scoped, opt-in, behavior-neutral-when-disabled instrumentation path, gated behind a separate contract amendment before any such code lands. Rollback at every stage is a plain git revert — no production behavior is at risk until a release explicitly earns write access to `renmark/**`/`plugin/**` through its own contract.

## Consequences

- Renmark's own development now runs under the same release-oriented, role-authority-bounded methodology it will eventually offer for every project it builds (PRD REQ-27) — this is deliberate dogfooding, not a special process reserved for this refactor.
- The next release-lifecycle decision point is R-0.0's own acceptance: this ADR, the benchmark task definitions (WP-3), the telemetry coverage analysis (WP-4), and the baseline evidence (WP-5) are jointly evaluated against the internal acceptance scenario in `../milestones/R-0.0/internal-acceptance-scenario.md`.
- Nothing in this ADR is binding on `renmark/**`/`plugin/**` production code until a release's own contract explicitly authorizes a change there.
