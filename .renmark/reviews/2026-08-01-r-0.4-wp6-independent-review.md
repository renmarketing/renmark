# R-0.4 WP-6 — Independent Review: Minimal Independent Inspector (WP-1..WP-5)

## Verdict: ESCALATE

## Scope checked

Commits `ba84e64` (WP-1 design/role), `e953ae4` (WP-2 enforcement),
`83d7c8f` (WP-3 emit/read helpers), `7976c01` (WP-4 wiring), `2708ba0`
(WP-5 tests), against the R-0.4 contract's Scope / User journey /
User acceptance sections.

## Findings

1. **The dispatch-independence check itself is real, mechanical, not
   prompt-only. CONFIRMED with fresh, non-mocked execution.**
   `check_dispatch_independence` (`renmark/ledger.py:331-378`) raises
   `DispatchIndependenceError` when `inspector_dispatch_identity` is
   empty/blank, and when it equals a non-empty
   `work_result_dispatch_identity`; it does not raise when only the worker
   identity is empty. `emit_inspection_verdict` (`renmark/ledger.py:447-503`)
   calls this check as its first statement (line 478-480), before
   constructing or appending anything, and does not catch/swallow the
   exception — it propagates unchanged. I independently ran a throwaway
   script (not committed) against a temp repo: same-identity call raised
   `renmark.ledger.DispatchIndependenceError: inspector dispatch_identity
   'codex:wo-1' matches the work result's dispatch_identity; a dispatch
   cannot independently inspect its own work`, with zero ledger events
   written afterward; a distinct-identity call succeeded and
   `latest_verdict_for` read back `dispatch_identity='renmark-verifier'`,
   `verdict='pass'` correctly. `tests/test_ledger.py` (7 new R-0.4 cases,
   lines 204-273) assert the raised exception type directly via
   `pytest.raises`, not a mock or a comment.

2. **The wired call site (`renmark/cli/_engine.py:670-766`, `_runner`)
   correctly sets a real per-task `dispatch_identity` on `WorkResult`
   (`f"{task.executor or 'unknown'}:{order_id}"`, line 716) and a
   structurally distinct constant (`_INSPECTOR_DISPATCH_IDENTITY =
   "renmark-verifier"`, line 160) for the Inspector side. The independence
   check runs unwrapped (lines 743-747); only `_DispatchIndependenceError`
   is caught, and on catch it prints a WARNING and skips the ledger append
   — it does not silently accept a self-graded verdict. Only the ledger
   *write* (`append_ledger_event` inside `emit_inspection_verdict`) is
   wrapped in bare `except Exception: pass`, matching the established
   best-effort I/O convention from R-0.3. Confirmed correct as far as it
   goes.

3. **Material gap: WP-4's "real call site" is not an independent
   dispatch/judgment — it is a relabeled copy of the Worker's own verifier
   boolean, computed synchronously inside the same `_runner` closure.**
   The verdict written is literally `"pass" if ok else "fail"` where `ok`
   is the same boolean `_execute_task` already returned to the Worker's own
   `WorkResult` a few lines above (line 759, using the `ok` from line 701).
   No second `Agent`/executor call, no invocation of `plugin/agents/
   inspector.md` (the LLM Inspector role built in WP-1), and no new
   judgment of any kind occurs — only the `dispatch_identity` string
   differs, by construction (a hardcoded constant vs. an f-string), not
   because a second, independent process ever evaluated the work.
   This directly contradicts the contract's own "Expected result" wording
   (`.renmark/plans/2026-08-01-r-0.4-minimal-independent-inspector-contract.md`
   lines 156-160): *"a Work Result... has a corresponding Inspection
   Report event, produced by a dispatch that is mechanically distinct from
   the Worker's dispatch (**a separate Agent/executor call**, not the same
   role re-asserting its own output)"*. What shipped is the same
   role/process re-deriving a verdict from data it already had, not a
   separate Agent/executor call. `plugin/agents/inspector.md` (the actual
   LLM Inspector, read-only, correctly built and registered in
   `subagent_profiles.py`) is never dispatched by any production call site
   — it exists but is currently dead weight in the shipped pipeline.
   The WP-2/WP-3 mechanism (identity comparison, reject-before-write) is
   genuinely sound and independently verified (Finding 1); what is not
   proven is that R-0.4 shipped "an Inspector verdict... not a self-graded
   PASS" in the sense the contract's User journey/Problem-addressed
   sections describe — it proved the *guard rail* works, not that a real
   independent *judgment* is occurring at the one wired call site.

4. **Test evidence is honest about what it proves.**
   `tests/test_ledger_wiring.py::test_execute_plan_emits_independent_
   inspection_verdict` (lines 141-170) correctly asserts two distinct
   `dispatch_identity` values on linked ledger events (`assert
   verdict.dispatch_identity != work_result_dispatch_identity`) — this is a
   true, non-mocked assertion on real appended JSONL rows. It does not
   claim to test an LLM Inspector dispatch, and neither the test file nor
   the WP-4 commit message overstate this (the commit message says
   "derived from the task's own verifier pass/fail outcome" plainly) — the
   overstatement is in the release contract's own acceptance language
   versus what WP-4 actually implemented, which is an Owner-level scope
   question, not a hidden defect.

## Escalation for Owner decision

The dispatch-independence *enforcement mechanism* (WP-1/WP-2/WP-3, and the
schema/role/registry plumbing) is real, tested, and correctly wired — not
prompt-only. The open question is scope, not correctness: is a
deterministic-verifier-derived verdict (same dispatch, relabeled identity)
an acceptable "minimal" proof of the mechanism for R-0.4, or does the
contract's explicit "a separate Agent/executor call, not the same role
re-asserting its own output" language require the shipped call site to
actually invoke `plugin/agents/inspector.md` before WP-4/R-0.4 can be
called complete? This is a scope-conformance judgment call the Owner should
make, not something WP-6 should silently pass or unilaterally fail.

## Follow-up items

- **F-R0.4-1** (new, tracked): wire at least one real call site that
  actually dispatches `plugin/agents/inspector.md` as a separate
  Agent/executor invocation (not a same-process boolean relabel), or amend
  the R-0.4 contract's "Expected result" language to explicitly permit a
  deterministic-verifier proxy as sufficient "minimal" proof. Either
  resolution is acceptable; leaving the gap undocumented is not.
