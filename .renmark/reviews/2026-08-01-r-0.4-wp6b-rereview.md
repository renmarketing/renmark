## Findings

1. **Contract wording amendment is present and internally consistent, not
   partial.** `grep -n "Agent/executor"
   .renmark/plans/2026-08-01-r-0.4-minimal-independent-inspector-contract.md`
   returns zero matches — no stale "separate Agent/executor call" language
   survives anywhere in the file. `grep -n "separate inspection execution"`
   returns exactly one hit, line 159, in the "Expected result" bullet, which
   also now states the deterministic independent-verifier rerun is the
   DEFAULT Inspector for R-0.4's scope and the LLM Inspector
   (`plugin/agents/inspector.md`) remains optional (lines 156-166). No other
   section (Scope, User acceptance, Work packages) references the old
   phrasing, so this is a real amendment, not a spot-fix.

2. **The wired call site now performs a genuine second, independent
   `run_verifier` subprocess call — confirmed by direct code reading, not
   asserted from the commit message.** `renmark/cli/_engine.py:762-766`
   calls `_run_verifier(task.verifier, cwd=_repo,
   timeout_s=task.verifier_timeout_s)` — a fresh invocation of
   `renmark.verifier.run_verifier`, which shells out via
   `subprocess.run(["bash", "-c", command], ...)` (`renmark/verifier.py:43-49`)
   every time it is called; nothing is memoized or cached. The Worker's own
   verifier run happens earlier and separately, inside
   `_execute_task_codex` at `renmark/cli/_codex_runner.py:644`
   (`vres = run_verifier(task.verifier, cwd=repo,
   timeout_s=task.verifier_timeout_s)`), whose `vres.ok` ultimately becomes
   the `ok` boolean returned to `_runner` (line 702-710) — this is the value
   the prior WP-6 review found being relabeled. Post-repair,
   `_emit_inspection_verdict` (lines 767-777) sources `verdict` from
   `fresh_result.ok` and `evidence` from `[fresh_result.tail]` —
   `fresh_result` is the WP-4b rerun's own `VerifierResult`, never `ok` or
   `reason` from the `_execute_task` tuple at line 702. This closes
   F-R0.4-1 as specified: two structurally separate `run_verifier` calls in
   two different modules, at two different points in the control flow, each
   producing its own independent result object.

3. **WP-2's dispatch-independence check is unmodified and still runs
   unwrapped before the verdict is emitted.** `git log -1 --format=%H --
   renmark/ledger.py` → `83d7c8f` (WP-3), predating the WP-4b commit
   entirely — `check_dispatch_independence` was not touched by the repair.
   At the call site, `_check_dispatch_independence(...)` (lines 750-755) is
   called unwrapped; only `_DispatchIndependenceError` is caught (line 756),
   printing a WARNING and skipping the verdict entirely — the fresh verifier
   rerun (line 762) sits inside the `else` branch, so a failed independence
   check still prevents any verdict (correct — a rejected self-grading
   attempt cannot fall through to a "fail" verdict written anyway). Only the
   ledger *write* (`_emit_inspection_verdict`'s own try/except at
   lines 767-779) is best-effort/never-raising, matching the established
   convention.

4. **New regression test is non-circular and proves the exact claim.**
   `tests/test_ledger_wiring.py::test_inspection_verdict_derived_from_independent_rerun_not_worker_ok`
   monkeypatches `_execute_task` to report `ok=True` ("worker claims
   success") while the plan's real `verifier:` field is the shell command
   `false` (always exit 1). The test asserts the WorkResult's `status` is
   `"complete"` (proving the Worker's own `ok` really was `True` and was
   recorded as such — not silently altered) AND that
   `latest_verdict_for(...).verdict == "fail"` (proving the Inspection
   verdict tracked the independent rerun, not the Worker's boolean). If the
   repair had regressed to relabeling `ok`, this test would fail with
   `verdict == "pass"`. This is a genuine, discriminating regression test,
   not a weaker mock-everything assertion.

5. **New finding (non-blocking): the independent verifier rerun is not
   proven read-only, only commented as such.** The WP-4b code comment at
   `renmark/cli/_engine.py:740-742` states the rerun is "a deterministic,
   read-only-by-convention re-check (this codebase's verifier commands are
   check/test commands, e.g. pytest/py_compile, not mutating ones)" — but
   nothing in `renmark/parser.py` (verifier is parsed as a free-form
   `str`, `renmark/parser.py:373-375`) or `renmark/verifier.py` validates or
   constrains verifier commands to be idempotent/side-effect-free. A plan
   whose `verifier:` field has side effects (writes a file, mutates state,
   is flaky/non-deterministic under repeat execution, or is simply
   expensive) will now execute twice per task in every real
   `execute_plan` run — once inside the Worker's own gating/retry path
   (`_codex_runner.py:644`) and again for the Inspector rerun
   (`_engine.py:762`) — with no enforcement, only a comment, backing the
   "read-only" assumption. This does not reopen F-R0.4-1 (the independence
   gap is genuinely closed) and is consistent with R-0.4's stated "minimal"
   scope, but it is real residual risk worth tracking as follow-up debt
   (parallel to the R-0.2 carried-dependency pattern already used in this
   contract), not something WP-6b should silently absorb into an
   unqualified PASS.
