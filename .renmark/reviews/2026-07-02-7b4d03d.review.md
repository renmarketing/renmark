# Codereview — cost-control-finish-lanes (2e3cf3e~1..HEAD)

**Verdict 1 — Spec-compliance**  
Spec: under-built — the finish-lane integration weakens verification on the `quick` lane and wires the new cost preview incorrectly, so the required finish-lane/cost-control behavior is not fully usable.

**Verdict 2 — Code-quality**  
Summary: `4 Major`, `1 Minor`, `0 Critical`, `0 Nit`

- `renmark/dispatch.py:262` — `Major` — `SubagentInput.role` is resolved and stored, but `to_dict()` drops it, so the actual dispatched packet never carries the role the new profile system is supposed to expose.  
  Fix: include `"role": self.role` in `SubagentInput.to_dict()` and add/adjust isolation tests to assert the serialized packet contains it.

- `renmark/finish_lanes.py:188` — `Major` — `resolve_lane()` only accepts exact lane names, but `finish/SKILL.md` tells users to answer with numbered choices like `1`/`2`/`3`, so non-recommended numeric selections silently collapse back to the recommended lane.  
  Fix: either teach `resolve_lane()` to accept menu aliases (`1`-`5`, bracket letters, empty input) or change the skill prompt to require exact lane names only.

- `plugin/skills/finish/SKILL.md:55` — `Major` — the new cost-preview wiring passes unsupported keys (`lane`, `cost_level`) into `estimate_cost()` and then later references nonexistent field `preview.estimated_cost`, so a literal implementation produces meaningless identical previews or breaks on the field access.  
  Fix: build the preview from concrete supported inputs or render lane cost directly from `lane_spec.cost_level`, and use the real dataclass field name `preview.est_cost_usd`.

- `plugin/skills/finish/SKILL.md:77` — `Major` — the `quick` lane explicitly skips re-verification and only confirms existing artifacts, which weakens verification despite the stated non-goal that verification must not be weakened.  
  Fix: keep `quick` as the cheapest lane by skipping merge/release/package/WSL work, but still run the normal verifier pass.

- `renmark/cost.py:154` — `Minor` — `estimate_cost()` treats `True` as a valid positive `int` because `bool` subclasses `int`, so garbage `est_tokens` can contribute `1` token instead of degrading cleanly to `0`.  
  Fix: reject booleans before the `isinstance(raw_tokens, int)` check, matching the defensive handling already used in `context_budget_hint()`.
