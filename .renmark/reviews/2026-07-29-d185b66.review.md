**Perspectives**
- Canonical-state lens: M1 is supposed to establish one delivery aggregate per run. The code defines the aggregate, but the legacy projection path does not keep a stable run identity before `delivery.json` exists.
- Migration/validation lens: the new module can emit persisted state that the new validator immediately rejects, so the “canonical” format is not self-consistent yet.
- CLI/read-only lens: the `--delivery-state` seam looks additive and non-mutating from static inspection; I did not find a write-side regression there.

**Assumptions**
- The acceptance bar is the M1 plan dated July 29, 2026, not the full eventual REQ-25 rollout.
- `run_id` is meant to identify the same in-flight delivery run across repeated reads and resume boundaries.
- `renmark.schemas.validate_delivery_state()` is intended to validate persisted `delivery.json`, not just hand-authored fixtures.

**Potential Edge Cases Checked**
- Legacy-only repos with `agency.json`/`lifecycle.json`/`program.json` but no `delivery.json`
- Older or migrated `delivery.json` payloads carrying non-v1 schema/contract markers
- Repeated deterministic inspection before any canonical delivery-state write

**Findings**
1. Major, blocking — legacy projection generates a fresh `run_id` on every read instead of a stable per-run identifier. Evidence: [lifecycle.py](/home/renmark/projects/ai-system/renmark/lifecycle.py:1201) builds the canonical summary from `default_delivery_state()`, and [delivery_state.py](/home/renmark/projects/ai-system/renmark/delivery_state.py:166) plus [delivery_state.py](/home/renmark/projects/ai-system/renmark/delivery_state.py:429) synthesize a new random `delivery-<hex>` whenever `run_id` is empty. Reproduced with `PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python - <<'PY' ... read_legacy_delivery_summary(...).delivery.run_id ... PY`, which printed two different IDs on consecutive reads (`same False`). This breaks the “one per-run aggregate” contract for any repo still on legacy state, and it makes resume/correlation logic unstable until some future writer persists `delivery.json`. Fix: derive a deterministic legacy run ID from persisted workflow state, or persist one once and reuse it on later projections.

2. Major, blocking — the delivery-state writer/reader and the delivery-state validator disagree on what persisted state is acceptable, so migration/canonicalization is incomplete. Evidence: [delivery_state.py](/home/renmark/projects/ai-system/renmark/delivery_state.py:427) preserves caller-supplied `schema_version`, `contract_version`, and `run_id`, while [schemas.py](/home/renmark/projects/ai-system/renmark/schemas.py:180) rejects any `schema_version` other than `1`, [schemas.py](/home/renmark/projects/ai-system/renmark/schemas.py:187) rejects any `contract_version` other than `delivery-state/v1`, and [schemas.py](/home/renmark/projects/ai-system/renmark/schemas.py:193) rejects non-`delivery-<12 lowercase hex>` IDs. Reproduced with `PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python - <<'PY' ... DeliveryState(schema_version=7, contract_version='delivery-state/v7', run_id='delivery-abc123') ... schemas.validate_delivery_state(...) ... PY`, which returned three validator errors for the state the module itself serialized. The tests currently lock this behavior in at [test_delivery_state.py](/home/renmark/projects/ai-system/tests/test_delivery_state.py:87). Fix: either canonicalize these fields on read/write so persisted state always validates, or add an explicit versioned migration path and make the validator accept supported legacy versions until migrated.

**Recommendations**
- Add a stable legacy `run_id` derivation rule and assert repeated `read_legacy_delivery_summary()` calls return the same ID for unchanged legacy state.
- Decide whether `delivery.json` is always canonical-on-disk or versioned-on-disk. Then align [delivery_state.py](/home/renmark/projects/ai-system/renmark/delivery_state.py) and [schemas.py](/home/renmark/projects/ai-system/renmark/schemas.py) to that choice instead of preserving values the validator rejects.
- Add one test for writer-to-validator compatibility and one for stable legacy run identity once the environment can execute pytest normally.
