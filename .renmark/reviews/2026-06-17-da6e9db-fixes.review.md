The fixes are not clean; the hook hardening and the report/rollback changes still leave real bugs.

- Critical — [renmark/scan.py:675](/home/renmark/projects/ai-system/renmark/scan.py:675): the new hook only recognizes a literal top-level `git` token, so it fails open for `/usr/bin/git commit`, `env git commit`, `command git commit`, and wrapper forms like `bash -c "git commit"`, `sh -c "git push"`, and `eval "git commit"`. Fix: normalize executable basenames and either recursively inspect shell-wrapper payloads or reject wrapper/eval forms outright in read-only mode.

- Critical — [renmark/scan.py:729](/home/renmark/projects/ai-system/renmark/scan.py:729): the hook only tokenizes outer shell segments, so nested command execution via `$(git commit ...)` and backticks passes unchecked and mutates the repo. Fix: fail closed on command substitution/backticks or switch to a real shell parser/AST that inspects nested command nodes before allowing execution.

- Major — [renmark/scan.py:416](/home/renmark/projects/ai-system/renmark/scan.py:416): `_report_rel_path()` is still not unique, because the hash omits `checks_failed_to_run` and there is no nonce, so two same-second scans with the same findings, or the same findings but different failed checks, collide and overwrite the artifact. Fix: include a true per-write unique component or hash the full rendered report state, including `checks_failed_to_run`.

- Major — [renmark/scan.py:374](/home/renmark/projects/ai-system/renmark/scan.py:374): `_ledger_lock()` silently degrades to unlocked execution when the lock file cannot be opened or `flock()` fails, so the advertised concurrent-scan safety disappears with no signal and duplicate proposals can reappear under lock failure. Fix: surface lock-degraded mode explicitly in the CLI/report/logs and do not claim serialization succeeded when no lock was acquired.

- Major — [renmark/scan.py:590](/home/renmark/projects/ai-system/renmark/scan.py:590): `_propose_one()` assumes `backlog.next_id()` always reserved a placeholder, but `next_id()` can degrade to an unreserved computed id on `os.open` failure or retry exhaustion, so `_rollback_reserved()` can unlink a legitimately created item claimed by another writer in the gap. Fix: have `next_id()` return reservation status and only unlink on rollback when this call actually created the reservation.
