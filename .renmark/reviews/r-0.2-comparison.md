# R-0.2 — Engineering Acceptance Comparison

Fresh `pytest -q` run (this session, this sha): **1726 passed, 31 skipped, 0
failed.** Matches WP-5e's cited count — independently reproduced, not just
re-cited.

Method: for each criterion I read the design doc's claim, then the actual
`renmark/**`/`plugin/**` code (not the status-note prose), then confirmed
whether the mechanism is (a) implemented, (b) tested, and (c) **wired into a

## Criterion-by-criterion

### 1. Normal-path Worker scope enforcement (Scenario-C reproduction)

> "A Worker dispatched through the NORMAL (non-fast-path) route with a
> declared scope cannot perform a file operation outside that scope without
> being blocked or triggering explicit escalation."

**PARTIAL.**

- `renmark/providers/claude_agent.py::build_agent_dispatch()` gained an
  optional `scope: WorkerScope | None = None` kwarg; `renmark/dispatch.py`'s
  new `verify_agent_dispatch_scope()` reuses `fast_path.verify_worker_scope`
  unchanged. Both are correctly implemented and directly proven by
  `tests/test_dispatch_scope_generalization.py::
  test_scoped_dispatch_out_of_scope_delete_fails_verification` — a
  synthetic Scenario-C reproduction that does fail verification as
  designed.
- **But:** `grep -rn "verify_agent_dispatch_scope" --include=*.py .` and the
  same for `build_agent_dispatch(...scope=` outside `tests/` return **zero**
  production call sites. No skill, no CLI entry point, no
  `renmark/program_driver.py` code path ever populates `AgentDispatch.scope`
  or calls the post-hoc verifier for a real dispatch. Unlike R-0.1's WP-5,
  which cited a live subagent run in addition to the synthetic test, R-0.2
  has no live-dispatch evidence — only the unit test.
  `scope-enforcement-generalization-design.md` §5 explicitly recommended
  "Option A: default scope = no enforcement, gradual opt-in" for backward
  compatibility, so this is a deliberate, documented choice, not a hidden
  bug — but it means the contract's "Expected result" (a live Worker
  blocked on the normal path) has not actually happened yet.
- Multi-wave/cumulative scope verification (design doc §3, Options A/B/C)
  is explicitly undecided and unimplemented (WP-5a status note). This
  criterion's wording is single-dispatch, so the multi-wave gap doesn't by
  itself sink it — the zero-wiring gap does.

### 2. Inspector cannot repair — separate logged work order

> "An Inspector-role finding never results in a direct file mutation by
> that same role — demonstrated by a reproduction where a reviewer surfaces
> a defect and a SEPARATE, logged work order performs the fix."

**PARTIAL** (split verdict within one criterion).

- **Tool-restriction half — PASS, mechanically verified directly:**
  `plugin/agents/reviewer.md` frontmatter reads `tools: Read, Grep, Glob,
  Bash` (no `Write`, no `Edit`) — read directly, not trusted from a status
  note. A reviewer-role dispatch structurally cannot call `Write`/`Edit` in
  the same context. This is a real, mechanical improvement over R-0.1's
  and WP-6's cited pre-WP-5c state (`Read, Grep, Glob, Bash, Write`).
- **"Separate, logged work order performs the fix" half — NOT
  demonstrated end-to-end:** `renmark/dispatch.py`'s new
  `InspectorFinding`/`RepairWorkOrder`/`build_repair_work_order()` are a
  correct, well-tested pure data transform (8 tests in
  `tests/test_repair_work_order.py`, including severity/verdict gating and
  scope reuse). But `build_repair_work_order` has zero non-test callers,
  no ledger/logging emission exists (per design doc §4.3's Governor
  integration, "explicitly deferred" — WP-5e status note), and
  `grep -rln "RepairWorkOrder\|repair work order" plugin/skills/` returns
  nothing — design doc §4.2's mandated "Inspector findings do not
  self-repair" clause was never added to `codereview`, `finish`, or
  `verify` SKILL.md. No skill actually emits, routes, or logs a repair
  work order today.
- Net: the "cannot mutate" half of R-006 is genuinely PASS; the
  "separate, logged work order performs the fix" half is untested outside
  a unit test of the data shape — the criterion as a whole is PARTIAL.

### 3. Every dispatch carries reason/scope/budget, rejected pre-inference if missing

> "demonstrated by a dispatch attempt missing one of these being rejected
> before any inference call is made."

**PARTIAL, leaning NOT MET as literally worded ("every... dispatch...
carries").**

- `renmark/subagent_gate.py` gained `R008Checklist`, `validate_r008_dispatch`,
  `enforce_r008_dispatch(strict=...)`, `R008DispatchRejected` — correctly
  implemented, and `enforce_r008_dispatch(spec, strict=True)` does reject a
  dispatch missing any of the six fields, per
  `tests/test_subagent_gate_r008.py` (39 tests, direct rejection tests
  included).
- **But:** `enforce_r008_dispatch`/`validate_r008_dispatch` have zero
  non-test callers. Default mode is lenient (never rejects, per design doc
  §8.1's explicit "warning + inference" migration phase — WP-5b's own
  status note flags "wiring the validator into an actual dispatch call
  site... intentionally left for a follow-up"). No real dispatch anywhere
  in the codebase is actually gated by this check; strict mode is only
  exercised by unit tests calling the function directly. The literal claim
  "every Agent/executor dispatch... carries a machine-checkable reason,
  scope, and budget reservation prior to dispatch" is false today — no
  dispatch carries these fields at all in production.

### 4. Third materially-equivalent repair/replan stops uniformly (fast-path + normal)

> "uniformly across fast-path and normal dispatch."

**PARTIAL, "uniformly" NOT MET.**

- Real, verified progress since WP-4's own discovery: `decide_milestone_
  execution()` (`renmark/program_driver.py`) is now documented and tested
  as path-agnostic in its own body (no dispatch-type branch), and the
  three-attempt block is exercised uniformly by direct calls in
  `tests/test_replan_evidence_gate.py::
  test_third_equivalent_repair_cap_fires_identically_from_different_callers`.
- **But:** per the function's own docstring (`program_driver.py` line
  ~383) and confirmed by grep: "Only `plugin/skills/orchestrate/SKILL.md`'s
  prose currently calls it in production; wiring it into additional Python
  dispatch call sites... is a future, separately-scoped integration." Fast
  path itself does not call it (`grep` on `renmark/fast_path.py` for
  `decide_milestone_execution`/`recurrence` returns nothing), and
  `/renmark:feature`/`/renmark:start`/`/renmark:debug` SKILL.md files
  reference `program_driver.py` only for stage sequencing, not this
  function. Even the one production caller (`orchestrate`) is a **prose
  instruction to an LLM**, not a mechanically enforced Python call site —
  materially weaker than "a dispatch attempt... rejected before any
  inference call" language used elsewhere in this same contract. "Uniformly
  across fast-path and normal dispatch" is not actually true yet.

### 5. Replan rejected unless an evidence-backed trigger is present

**PARTIAL**, same "built correctly, unwired" pattern as #1/#3.

- `renmark/program_driver.py`'s new `permit_replan()`/`ReplannableEscalation`/
  `ReplanDecision`/`MAX_REPLANS_PER_MILESTONE` are a correct, thorough
  implementation of all 5 triggers plus artifact-existence, staleness, and
  per-milestone frequency-cap checks — 11 tests in
  `tests/test_replan_evidence_gate.py` cover permit/reject cases for each
  trigger, a prose-only-assertion rejection, a missing-artifact rejection,

- **But:** `permit_replan` has zero non-test callers; no skill ever
  constructs a `ReplannableEscalation` or routes a replan request through
  this gate. The gate is real and correct in isolation but has never
  actually been invoked to permit or reject a live replan decision.

## Additional observations (per dispatch scrutiny list)

1. **No-nested-dispatch (R-007) — not one of the 8 acceptance bullets, but
   directly relevant to criterion framing.** WP-6's finding is independently
   confirmed: all 8 `plugin/agents/*.md` files' `tools:` lines omit
   `Agent`/`Task` (grep-verified directly, not just cited). This is a real,
   structural upgrade over R-0.1's prompt-only guarantee for the 8 native
   roles. It remains prompt-level-only for the `general-purpose` fallback
   and unconfirmed for Codex — WP-6 documents this honestly rather than
   claiming full closure. Correct posture; carry forward as a follow-up,
   same as R-0.1's F1.
2. **Multi-wave/cumulative scope verification (WP-1 design doc §3)** was
   explicitly deferred by WP-5a. No engineering-acceptance criterion
   literally requires the multi-wave case (#1 is phrased at single-dispatch
   granularity), so this deferral does not sink any of the 8 criteria by
   itself — but it does mean scope enforcement, even once wired, would
   still not cover `/renmark:orchestrate`'s actual multi-wave shape without
   further work.
3. **Repair-work-order pattern (WP-5e) is a pure data-transform.** The
   "Inspector cannot repair" criterion's tool-restriction half is
   mechanically satisfied today (see #2 above) independent of whether the
   work-order pattern is wired — that part of R-006 does not need the
   Governor/skill wiring to be true. The "separate, logged work order
   performs the fix" half of the same criterion, however, does depend on
   that wiring, and it is not done.
