## 1. BACKLOG — Item schema, storage, and append API

### Item schema (renmark/backlog.py:80–104)

BacklogItem dataclass (all fields str, JSON-trivial):

  id: str              # BL-NNNN (zero-padded 4 digits)
  title: str
  status: str          # one of STATUSES (default "needs review")
  source: str          # free string; expected: "user"|"qa"|"research"|"bug"|"idea"
  risk: str            # free string; expected: "low"|"medium"|"high"
  summary: str
  evidence_path: str   # path to evidence artifact — never read into conversation
  recommended_action: str
  served_requirements: str
  pending_decision: str
  branch: str
  loop_id: str
  disposition: str     # "" while open; one of DISPOSITIONS once terminal
  created_at: str
  updated_at: str

### Storage location

.renmark/state/backlog/BL-NNNN.json
Path: backlog_dir(repo) → state_dir(repo) / "backlog"
(renmark/backlog.py:113–117)

### Append API — three-step pattern (already documented in SCHEDULED-QA.md:46–61)

Step 1 — allocate an ID:
  from renmark.backlog import next_id
  item_id = next_id(repo)   # atomic O_CREAT|O_EXCL reservation → BL-NNNN

Step 2 — construct the item:
  from renmark.backlog import BacklogItem
  item = BacklogItem(
      id=item_id,
      title="...",
      status="needs review",      # ALWAYS for proposer lane
      source="qa",                # tags the lane
      evidence_path=".renmark/reviews/...",
      risk="low|medium|high",
      summary="...",
      recommended_action="...",
      created_at="ISO8601",       # caller must pass — module never calls datetime.now()
      updated_at="ISO8601",
  )

Step 3 — persist:
  from renmark.backlog import write_item
  write_item(repo, item)  # atomic tmp→replace; returns Path or None; never raises

Functions: next_id (backlog.py:165), write_item (backlog.py:309), BacklogItem (backlog.py:79).
The seam is deliberately narrow — the proposer's only mutation is a single write_item call.

### Deduplication — MISSING from current API

There is NO dedup helper in backlog.py. The list_items() function (backlog.py:347)
returns all items sorted by created_at desc; the proposer must READ the list and
compare proposed titles/evidence_paths against existing items before calling next_id.
The comparison logic is the proposer's responsibility, not the module's.
This is a gap to flag: dedup strategy must be defined in the new skill spec
(e.g. exact title match, fuzzy, hash of evidence_path). list_items() is the read API.

## 2. READ-ONLY ENFORCEMENT — Precedent and mechanism

### audit skill (plugin/skills/audit/SKILL.md:boundaries section)

  "Read-only. Never advances lifecycle.json stage — audit is diagnostic, not a
   workflow transition. All writes inside .renmark/audits/."

Mechanism: CONVENTION ONLY, not enforced by code. The audit engine (renmark/audit.py)
is pure reading + artifact writing; it simply does not call lifecycle.write_lifecycle()
or git. There is no capability profile, permission guard, or sandbox flag enforcing this.
The boundary is maintained by the SKILL.md contract and the audit module's design.

### codereview skill (plugin/skills/codereview/SKILL.md)

  "codex exec --sandbox read-only -"

Mechanism: codex's --sandbox flag when running the full codex pass. This IS
an enforced sandbox for the codex subprocess, but the surrounding skill is still
convention-only (it could call lifecycle.write_lifecycle — it just doesn't, per spec).
The skill does write lifecycle stage (reviewed) after a full codex pass, which is a
lifecycle advance — so codereview is NOT a pure read-only skill; it advances on a
code path. The --sandbox read-only flag applies only to the codex subprocess.

### Conclusion: no reusable read-only capability profile

There is no ReadOnlySandbox class, no permission_profile() helper, no enforced boundary.
Both audit and codereview rely on skill-level convention. The proposer lane must enforce
read-only by the same mechanism: SKILL.md contract + module design (never call
lifecycle.write_lifecycle, never call git commit/merge/branch, never edit product files).
ASSESSMENT: Convention-only, not a reusable enforced primitive. REQ-14 must define its
own read-only contract in the skill doc and uphold it through module design.

## 3. CHECK SURFACES — Programmatic invocability

### renmark.audit — FULLY PROGRAMMATIC

run_audit(repo, quick=False) → AuditReport (renmark/audit.py:468)
  Returns structured AuditReport.passes dict (pass_name → [issue strings]),
  modularity_counts, inventory_count, total_issues, ok (bool), verdict ("PASS"|"ISSUES").
  Importable, zero-LLM, never raises into caller.

build_inventory(repo) → list[CommandEntry] (renmark/audit.py:142)
  Returns per-command flat inventory. Pure parsing, no LLM.

write_audit_report(repo, report) → {"md": path, "json": path} (renmark/audit.py:571)
  Writes artifacts to .renmark/audits/ via summary.write_artifact.

CLI: python -m renmark.audit [--quick] [--inventory-only] [--json] [--repo PATH]
  Exit 0 = PASS, 1 = ISSUES. Bounded ≤5-line stdout.

VERDICT: audit IS a programmatic check surface the proposer can import and call directly.
It returns structured findings — not skill-only.

### renmark.verifier — PROGRAMMATIC RUNNER, not a structured findings surface

run_verifier(command, *, cwd, timeout_s=60, tail_lines=50) → VerifierResult
  (renmark/verifier.py:28)
  VerifierResult: exit_code, output, tail, timed_out, ok(bool)

This is a subprocess runner for individual shell commands. It does not expose
"QA findings" or "structured QA results" — it runs one command and returns exit code +
tail. To run verify --qa / --deep-qa programmatically, the proposer must invoke the
full /renmark:verify skill (via Agent dispatch or python -m renmark.__main__ equivalent)
since the QA flow logic (browser driving, pass criteria, artifact writing) is in the
SKILL.md, not in a callable Python module.

summary.verifier_tail(cmd, cwd, tail_lines=3) → str (renmark/summary.py:314)
  G3-compliant wrapper — same subprocess runner, returns a bounded single line.

VERDICT: verifier is a low-level subprocess runner. It can run pytest/lint/ruff as
individual commands. For the proposer's "run checks" use case (pytest, ruff, mypy),
summary.verifier_tail() is the right API. The full /renmark:verify --qa flow is
skill-only — it cannot be called as a Python function.

### renmark.lint, renmark.modularity, renmark.release — PROGRAMMATIC (via run_audit)

lint.lint_all(plugin_dir, include_frontmatter_strict=True) → list[str]
modularity.analyze(repo) → list[Gap]
release.drift_report(repo) → list[str]

These are all composed by run_audit() — the proposer should call run_audit() rather than
these primitives individually.

## 5. LIFECYCLE/DOMAIN — Where does the proposer skill belong?

### Current DOMAIN_BY_SKILL (renmark/lifecycle.py:105–132)

  "audit" domain: audit, inventory
  "build" domain: start, brainstorm, plan, check-plan, orchestrate, verify, finish,
                   feature, prd, blueprint, backlog, loop
  "meta" domain: setup, roadmap, help, resume, approve, hygiene, doctor, init, usage, analytics

### Where should the proposer lane go?

Option A — "audit" domain (audit, inventory + new proposer skill):
  PRO: The proposer reads and checks (like audit), writes to .renmark/audits/ or
  .renmark/reviews/, never advances lifecycle. Domain semantics match.
  CON: It also proposes into the backlog (one write_item call), which is a build-domain
  artifact. But write_item is a single ledger write with status="needs review", not a
  lifecycle advance — audit domain is still the right fit.

Option B — "build" domain:
  CON: The proposer never builds; it is explicitly read-only. Domain mismatch.

Option C — "meta" domain:
  CON: Meta is for plugin management (setup, help, resume). The proposer is an operational
  QA lane, not a plugin meta skill.

RECOMMENDATION: "audit" domain. Add the new skill name (e.g. "qa-propose" or "propose")
to DOMAIN_BY_SKILL["audit"] and to IMPLEMENTED_SKILLS and AUX_SKILLS (it is a terminal,
read-only skill — class 3 aux).

### lifecycle.py changes needed (3-line addition once skill is named)

  DOMAIN_BY_SKILL: add skill_name -> "audit"
  IMPLEMENTED_SKILLS: add skill_name
  AUX_SKILLS: add skill_name (class 3 — terminal, never advances stage)

skill_preamble(repo, skill_name) will then correctly detect cross-domain transitions
(e.g. from "build" → "audit" domain on scheduling) and surface the /clear hint.

## 6. EDGE CASES AND ASSUMPTIONS

### Blocking issues

1. DEDUP IS UNIMPLEMENTED — No dedup API in backlog.py. The proposer must read
   list_items() and apply its own dedup strategy before calling next_id(). If not
   handled, the same QA gap will be filed repeatedly on each scheduled run.
   Dedup strategy must be specified in the REQ-14 skill spec.

2. SCHEDULING MECHANISM IS UNIMPLEMENTED — PRD says "scheduled subagents"; there is no
   CronCreate/scheduler Python module in renmark/. The scheduler must come from outside
   (Claude Code CronCreate skill, external cron, etc.). The proposer skill itself is
   invocable — the scheduling mechanism is the gap.

3. VERIFY --QA IS SKILL-ONLY — The browser-driven QA flow logic is in SKILL.md, not a
   callable Python fn. The proposer can run lint/test/type-check via verifier.run_verifier
   or summary.verifier_tail, but cannot programmatically run /renmark:verify --qa as a
   function. Must dispatch via Agent or use python -m renmark audit for the audit surface.

### Deferrable

4. REPORTS SUBDIRECTORY COLLISION — .renmark/reports/ is for feature reports (REQ-15).
   The proposer should NOT write there; it should use .renmark/reviews/ (verify uses this)
   or .renmark/audits/ (audit uses this). No collision risk if this convention is respected.

5. DOMAIN REGISTRATION — lifecycle.py DOMAIN_BY_SKILL, IMPLEMENTED_SKILLS, AUX_SKILLS
   must be updated when the skill is named and added. This is a 3-line addition.

6. CREATED_AT MUST BE PASSED BY CALLER — BacklogItem does not call datetime.now();
   the proposer must obtain the timestamp from renmark.state.now_iso() and pass it.
