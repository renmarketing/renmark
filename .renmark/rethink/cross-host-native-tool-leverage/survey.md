# Survey: cross-host native-tool leverage

## 1. Host-detection/capability machinery (`renmark/hosts.py`)

`HostKind` enum: `CLAUDE_CODE = "claude"`, `CODEX = "codex"`, `UNKNOWN = "unknown"` (hosts.py:16-21). Only two real hosts are modeled; `UNKNOWN` is the extension point for a third host — it gets a conservative all-`False` capability set (no selector, no clear/resume/compact) rather than inferring anything (hosts.py:68-78). `_HOST_ALIASES` (hosts.py:81-88) maps string aliases (`claude-code`, `claude_code`, `openai-codex`) onto the two known kinds — adding a third host means adding a `HostKind` member, a `_CAPABILITIES` entry, and alias strings; no plugin registry, just this one file.

`resolve_host()` (hosts.py:91-111) precedence: explicit `host` arg > `RENMARK_HOST` env var > `CODEX_THREAD_ID`/`CODEX_INTERNAL_ORIGINATOR_OVERRIDE` env markers > default `CLAUDE_CODE`. An unrecognized explicit/env string resolves to `UNKNOWN`, not to a guess.

`capabilities_for()` (hosts.py:114-163) returns a `HostCapabilities` dataclass: `render_surface`, `selector_tool`, `selector_available`, `selector_min/max_options`, `supports_numbered_selector`, `supports_clear`, `supports_resume`, `supports_compact`. Claude Code: `selector_tool="AskUserQuestion"`, `selector_available=True`, `supports_clear/resume/compact=True`. Codex: `selector_tool="request_user_input"`, `selector_available=False` (Codex Default mode doesn't expose it), `supports_clear/resume/compact=False`. A `render_surface="codex-plan"` override re-enables the selector (hosts.py:147-151) — the one documented case where render surface, not host identity alone, changes selector availability.

## 2. Every place renmark branches on host identity

- `renmark/hosts.py:91-111` — `resolve_host`, the canonical branch point everything else calls into.
- `renmark/interaction.py:152-230` (`build_selector`) — the real behavioral fork: resolves host, pulls capabilities, and if `caps.selector_tool is None` (Codex, no override) falls back to a numbered list; if a native selector exists, builds host-shaped native-tool arguments (Codex gets `request_user_input`-style args at ~line 230 onward).
- `renmark/dispatch.py:1057-1145` (`build_host_dispatch_plan`, `build_host_dispatch_plan_with_scope`) — for Codex builds `spawn_agent`/`wait_agent`/`followup_task` transport calls (dispatch.py:1108-1120); for Claude reuses the plain `Agent`-call path. `build_host_dispatch_plan_with_scope` (dispatch.py:1122 area) explicitly notes: `host == "codex"` intentionally leaves `scoped_dispatches` empty per a 2026-08-05 Owner decision — Codex gets no pre-action scoping this release, Claude does.
- `renmark/global_routing.py:113-131` — `_routing_block` branches text/config by resolved host.
- `renmark/lifecycle/preamble.py:205-210` — emits the `CONTEXT_GATE_CLEAR:`-prefixed string only when the host supports clear/resume (Claude Code); on Codex or `UNKNOWN` it records the invocation and emits no clear/resume gate.
- `renmark/behavior.py` (deterministic-tier eval harness) exercises both host paths explicitly at lines 811-812, 941, 1001, 1041-1122 — building selectors and running the eval harness once per host to assert the fork behaves as documented. This is test/behavior-verification code, not production routing, but it is the one place both host paths are exercised together in one file.
- `renmark/subagent_gate.py:462, 489, 520, 576, 616, 633, 724` — envelope/spend verdict functions take a `host` parameter (default `"claude"`) but from a skim, do not branch logic differently per host value inside the gate checks themselves — host is threaded through mostly for logging/status text (`control_status(control, host)`), not for a different gate decision. Worth flagging as a shallow host parameter (passed but not load-bearing) vs. the deep forks above.

Total distinct **decision points where behavior differs by host**: 5 (interaction.py selector fallback, dispatch.py transport shape + scope decision, lifecycle/preamble.py clear-gate emission, global_routing.py routing text, hosts.py capability table itself as the root). `subagent_gate.py`'s `host` param is present but not a differentiator — noted separately as shallow plumbing.

## 4. Claude Code native primitives renmark's skill prose assumes exist

Grep hits across `plugin/skills/` for `AskUserQuestion`, `TaskCreate`, `TaskUpdate`, `ScheduleWakeup`, `EnterWorktree`, `ExitWorktree`, `Agent`, `Workflow`: 28 files, notably `.shared/subagent-budget.md`, `.shared/task-tracking.md`, `.shared/usage-instrumentation.md`, `orchestrate/SKILL.md`.

- `AskUserQuestion` — **code-backed as a name** (`renmark/hosts.py:48`, `renmark/lifecycle/preamble.py:208`, `renmark/lifecycle/stage.py:648-655`) but never itself invoked from Python — by design, since it's a live-session tool call. `interaction.build_selector` constructs the argument shape a live session would pass to it. Real invocation is necessarily prose-directed (CLAUDE.md rule triggers it on `CONTEXT_GATE_CLEAR:`).
- `TaskCreate`/`TaskUpdate` — **explicitly prose-only, and renmark says so itself.** `plugin/skills/.shared/task-tracking.md:20-21,51-52,158-159,179-189` and `.shared/subagent-budget.md:35-43` are emphatic: in a live Claude Code session, the session itself must call the real `TaskCreate`/`TaskUpdate` tools — "not delegating it to a Python file." Grep of `renmark/` for these names returns **zero hits outside `hosts.py`/`lifecycle` comments** — confirmed no Python constructs these payloads. Instead, `renmark/task_tracking.py` (445 lines) implements a **separate, host-independent JSON-file mirror** (`.renmark/state/tasks.json`) of the same pending→in_progress→completed lifecycle, and its own docstring (task_tracking.py:1-7) says it models "the same lifecycle a host's native Task tools expose." `orchestrate/SKILL.md`'s prose (grepped) confirms the split explicitly: `renmark.task_tracking`'s Python mirror is wired specifically into the **codex/subprocess executor path** in `renmark/cli/_engine.py` (real call sites at `renmark/cli/_wave_loop.py:107,115,161,172,251,285,296,297,304,312`), used only where no live session exists to call native Claude tools — live Claude Code sessions are told to call the real `TaskCreate`/`TaskUpdate` tools directly instead. So this is not duplication so much as a deliberate host-conditional substitute — but it is the single largest hand-rolled mechanism whose entire reason to exist is "this host doesn't have a live session to call the real primitive."
- `ScheduleWakeup`, `EnterWorktree`/`ExitWorktree` — no hits found for `ScheduleWakeup` at all in `plugin/skills/` or `renmark/` (not referenced by renmark currently). `EnterWorktree`/`ExitWorktree` also produced no hits in this survey's greps of `renmark/` or `plugin/skills/` bodies — renmark's own worktree handling (`renmark/worktree.py`, section 5 below) is entirely custom subprocess-driven `git worktree` inspection, with no reference to a host-native worktree tool at all. This is a candidate gap: if Claude Code's `EnterWorktree`/`ExitWorktree` tools now exist as host primitives, renmark's worktree code was written without awareness of them.
- `Agent` / `Workflow` — heavily used, both prose (dispatch instructions throughout `plugin/skills/`) and Python-shaped (`renmark/dispatch.py` builds the packets `Agent`/`Workflow` calls consume). `plugin/skills/.shared/workflow-fanout.md` is the fullest treatment (section 6 below).

## 5. Hand-rolled mechanisms possibly duplicating a host primitive

**`renmark/heartbeat.py`** (194 lines): Polls `.renmark/state/PAUSED` and, when a `usage_limit` pause's `resume_after` window has passed, prints a nudge. `check()` (line 52) is pure/deterministic, delegates the actual check to `heartbeat_checks.run_all_checks`, never raises. `auto_resume()` (line 78) is a **pure subprocess delegation** to `renmark-execute --resume` — zero LLM calls itself. `emit_cron()` (line 108) only **prints** crontab/Windows Task Scheduler text; it never writes a file or installs anything. `is_cron_installed()` (line 176) greps `crontab -l` output, non-raising. This entire module is a home-grown scheduling/resume nudge system built on cron/Task Scheduler — there is no evidence renmark checked for or leverages a host-native `ScheduleWakeup` equivalent (none was found in section 4); this is worth flagging as duplicating capability an agent host might now offer natively.

**`renmark/usage.py`** (432 lines): `classify_usage_pause()` (line 312) is a pure classifier — computes `resume_after` via `_compute_resume_after` (line 268) from limits/events on disk and **returns** a `PauseState`; it does not itself write state or resume anything (the docstring literally says "No polling, no retry scheduling — purely computes resume_after and delegates"). Nothing in `usage.py` auto-resumes; resumption is entirely the optional, external `heartbeat.py --auto-resume` cron path — i.e., **the system writes a paused state and stops**; automatic resumption only happens if the user has separately installed a cron job. No host-native "wake me up" primitive is used or referenced.

**`renmark/worktree.py`** (303 lines) — every function is **read-only inspection**, none mutate: `_run_git`/`_default_branch` (helpers), `current_branch` (54), `_apply_worktree_line`/`list_worktrees` (68-125, parses `git worktree list --porcelain`), `is_clean_tree` (127), `diff_stat` (139), `divergence` (180), `is_merged` (208), `stale_worktrees` (221), `stale_local_branches` (266). Grep confirms **no `git worktree add`/`remove` calls anywhere in this file** — renmark never shells out to mutate worktrees itself; it only inspects state. That said, per section 4, this module also shows no evidence of using a host-native `EnterWorktree`/`ExitWorktree` tool for isolation — it's a parallel, subprocess-based, read-only status layer, not obviously in conflict with a host worktree tool but also not integrated with one.

**`renmark/task_tracking.py`** — see section 4. Full read: models `pending → in_progress → blocked/failed → completed/deleted` in a dataclass (`TaskRecord`, line 120) persisted atomically (`write_tasks`, line 186, via tempfile + `os.replace`) to `.renmark/state/tasks.json`. Enforces no-self-approval (`complete_worker_task`, line 351, requires an independently-dispatched verification task via `ledger.check_dispatch_independence`) and no-evidence-free completion (`complete_task` raises `MissingEvidenceError` without both `artifact_path` and `result_summary`, line 316). Real call sites are exclusively in `renmark/cli/_wave_loop.py` (10 call sites, lines 107-312) — i.e. only the headless/codex-subprocess execution path uses this Python mirror; a live Claude session is told (prose-only) to call real `TaskCreate`/`TaskUpdate` instead. This is intentional host-conditional design, not blind duplication, but it means **the "native task tracking" feature only has real Python callers on the Codex path** — for Claude Code, task tracking correctness depends entirely on the live model actually making the tool calls the skill prose asks for, with no deterministic enforcement.

**`renmark/dispatch.py`'s `build_host_dispatch_plan_with_scope` / `build_workflow_fanout_args`** — both real. `build_host_dispatch_plan_with_scope` (dispatch.py:1122-1160+) is confirmed a thin wrapper: calls `build_host_dispatch_plan` once (never duplicates its body), and for `host == "claude"` reuses `_maybe_scoped_claude_dispatch` to populate `scoped_dispatches`; for `host == "codex"` it intentionally leaves `scoped_dispatches` empty, citing an Owner 2026-08-05 decision that Codex gets no pre-action scoping this release and stays on the `verified_after`, Layer-B-only path (dispatch.py comment, ~line 1145). `build_workflow_fanout_args` (dispatch.py:934) pre-resolves each task's `agent_type` via `subagent_profiles.has_native_agent_file(role)` (subagent_profiles.py:293) so the Workflow script itself never needs Python import access.

`plugin/skills/.shared/workflow-fanout.md` (179 lines, read in full) documents renmark's **already-made** decision about adopting the Claude Code Workflow tool:
- **Adopts:** Workflow-tool fan-out only when a wave's non-codex task count is `> 1` (a single `needs_agent` task stays a plain `Agent` call — the `parallel()`/schema/`agentType` ceremony isn't worth it for one task). The Workflow script is a "thin dispatch shim" that does **no validation** of results (explicitly, so as not to create "a second, driftable copy of the G11 contract") — validation stays exclusively in `dispatch.parse_subagent_response()` in Python.
- **Explicitly declines to extend it to:** (1) `executor: codex` tasks — "A Workflow script has no filesystem/Bash access," so codex tasks stay on the `renmark-execute` subprocess path; (2) cross-`/clear` resumability — a Workflow's `resumeFromRunId` is same-session only and is explicitly *not* treated as a substitute for `.renmark/state/pipeline.json` checkpointing.
- **Cost/ledger note (rationale, not just description):** explicitly says NOT to use the Workflow tool's own budget/token-tracking for wave dispatch, because `state.log_agent_call` is the single ledger for Agent-path spend — using both would double-count tokens already covered by `cost.py`'s pre-dispatch estimate. This is a deliberate, reasoned rejection of a host-native accounting feature in favor of renmark's own ledger, to avoid double counting — not an oversight.

## 6. Feature use signals — is host-routing code exercised or dead?

`.renmark/analytics/task-runs.jsonl` (145 records) tracks an `executor` field (model tier), not a `host` field. Counted: `sonnet: 62, haiku: 45, codex: 33, opus: 5`. Grepping all three analytics JSONL files (`task-runs.jsonl`, `feature-runs.jsonl`, `events.jsonl`) for a `"host"` key returns **zero matches** — **renmark's analytics layer does not record which host (`claude` vs `codex`) actually dispatched a call, only which model tier was used.** Since `executor: "codex"` names a model-routing tier (a Codex CLI code-generation task) rather than the agent host, it is not safe to infer live-host split from this data at all — this is itself a finding: **the host-branching machinery in `hosts.py`/`interaction.py`/`dispatch.py` has no analytics signal proving which branch actually fires in production**, only `renmark/behavior.py`'s deterministic eval-tier tests exercise both `host="claude"` and `host="codex"` paths (confirmed, section 2) — that's test coverage, not live-use evidence.

## Pain and cost signals

- **TODO/FIXME/HACK density:** zero hits in `renmark/hosts.py`, `interaction.py`, `dispatch.py`, `codex_routing.py`, `task_tracking.py`, `heartbeat.py`, `worktree.py` — these files are clean of marker comments; whatever pain exists here is architectural, not left as inline debt markers.

- **`request_user_input` capability mismatch already self-documented:** `hosts.py` ships with `selector_available=False` for Codex and an explicit code comment admitting Codex Default mode doesn't currently expose the tool it's named after (hosts.py:29-32) — renmark is already carrying a known-stale assumption about a Codex primitive, correctly guarded by a capability flag rather than blind optimism.
- **No evidence of `ScheduleWakeup` or `EnterWorktree`/`ExitWorktree` awareness:** zero references anywhere in `renmark/` or `plugin/skills/` to these host tool names (section 4), while renmark hand-rolls the equivalent functionality itself (`heartbeat.py`'s cron-based wake-up nudge; `worktree.py`'s subprocess-based git worktree inspection). If these host primitives exist and are usable now, this is the highest-leverage "we built our own version before checking" candidate in the survey.
