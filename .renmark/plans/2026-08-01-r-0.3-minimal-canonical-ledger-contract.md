  though no live caller constructs one yet — schema readiness, not wiring.

## User value

- **Actor**: The Owner and any future Renmark session (including a
  resumed/cleared one) inspecting what actually happened during a build.
- **Capability**: Every Work Order, Work Result, Inspection Report, and
  Escalation produced by any pipeline is a schema-validated, append-only
  ledger event instead of scattered `.renmark/reviews/*.json` /
  `.renmark/plans/*.md` prose with inconsistent shape. A session can
  reconstruct "what was ordered, what came back, what was inspected, what
  was escalated" from one ledger stream without re-reading conversation
  history or guessing artifact shape.
- **Problem addressed**: today these four artifact kinds exist only as
  free-form files (reviews as ad hoc JSON, work-order-like instructions as
  prose inside SKILL.md dispatch packets, escalations as PAUSED-file prose)
  with no shared schema and no single append-only record. R-0.2's F2/F5
  follow-ups showed this concretely: a repair work order and a replannable
  escalation exist as *library functions* but have no canonical artifact
  shape to emit into, which is part of why nothing calls them yet.

## User journey

- **Starting state**: Post-R-0.2 (v0.39.5). Work orders, worker returns,
  inspection reports, and escalations each have ad hoc representations
  (dispatch packets, `.renmark/reviews/*.json`, PAUSED-file prose) with no
  shared schema and no append-only ledger.
- **Action**: A pipeline (orchestrate, debug, feature, etc.) emits a Work
  Order when dispatching, a Work Result when a Worker returns, an
  Inspection Report when a reviewer/verifier runs, and an Escalation when a
  blocker/pause/replan-worthy event occurs. Each emission is validated
  against its schema and appended to the ledger.
- **Expected result**: `.renmark/ledger/events.jsonl` (or equivalent path)
  contains a chronological, schema-valid record of these four artifact
  kinds for any pipeline run exercised during R-0.3's acceptance scenario.
  A read of the ledger alone (no conversation, no git log) answers "what
  was ordered, what came back, what was inspected, what was escalated" for
  that run.
- **Failure behavior**: a malformed emission (schema validation failure) is
  rejected, logged, and does not silently corrupt the ledger; the emitting
  pipeline surfaces the validation error rather than proceeding as if the
  event were recorded.

## Scope

- **Included**: JSON-schema definitions for Work Order, Work Result,
  Inspection Report, Escalation; a schema-validation helper; an
  append-only ledger writer (`ledger/events.jsonl`); wiring at least one
  real emission point per artifact kind (not all call sites — bounded
  proof, not universal rollout); a reader/query helper for `resume`-style
  consumption; tests for schema validation + append-only behavior.
- **Excluded**: blueprint schema; full milestone-contract schema; milestone
  closeout schema; ledger snapshot/restore; artifact content-hashing;
  migration adapters for existing plan/review/memory artifacts; universal
  rewiring of every dispatch path to emit ledger events (bounded proof
  only, matching R-0.1/R-0.2's "at least one real call site" precedent);
  closing F1/F2/F4/F5 (tracked only, per "Carried dependencies" above).
