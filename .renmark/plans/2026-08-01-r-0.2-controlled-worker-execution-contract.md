## User value

- **Actor**: The Owner, dispatching any task through Renmark's existing
  single-command interface — not only fast-path-eligible small tasks.
- **Capability**: Every Renmark-dispatched agent, on every path (fast path
  and normal/architectural), operates inside an enforced authority
  boundary: a Worker that hits ambiguity or a failing test cannot silently
  expand its own scope or replan the task itself; an Inspector that finds a
  defect can only report it, never patch it; every dispatch is traceable to
  an explicit reason, scope, and budget reservation instead of being issued
  ad hoc; and a request to redo work that already failed twice in the same
  way stops for an Owner decision instead of looping a third time.
- **Problem addressed**: R-0.1 (per its closeout, follow-up F1) proved the
  *fast path's* nested-dispatch prohibition is prompt-level only — it
  constrains one narrow class of tasks. Outside the fast path, R-0.1's WP-3
  regression baseline shows normal and architectural dispatch is unchanged
  from pre-R-0.1 behavior: no scope enforcement, no dispatch-reason/budget
  requirement, no mechanical separation between "Inspector finds a bug" and
  "Inspector fixes a bug," and no cap distinguishing a legitimate second
  repair attempt from an open-ended retry loop. Per
  governing-architecture-roadmap.md §2 this is the exact overhead source the
  whole refactor was commissioned to fix: agents replanning settled
  decisions and spending more inference managing the workflow than
  implementing the feature.

## User journey

- **Starting state**: Renmark v0.39.4 (post-R-0.1). Fast-path tasks get
  WorkerScope enforcement (`verify_worker_scope` against real `git diff`)
  and a contractual (not mechanical) no-nested-dispatch rule. Every other
  dispatch path — normal `/renmark:feature`, `/renmark:debug`,
  `/renmark:orchestrate` multi-wave runs — has none of R-005/R-006/R-007/
  R-008/R-012 enforced; only the platform's own permission classifier is in
  the loop, same as the gap R-0.0's Scenario C originally found.
- **Action**: Owner issues any task, of any size or shape. General
  Contractor dispatches through the existing routing (fast path or normal),
  and every dispatch — regardless of path — now carries a bounded
  work-order record (reason, declared scope, budget) that the Governor
  validates before dispatch and re-validates after return, per addendum-01
  §9.3/9.4. An Inspector-shaped finding (from a review/verify/QA step) can
  only produce a structured PASS/FAIL/finding, never a direct file
  mutation. A Worker that reports it wants to change its own scope or
  approach mid-task is rejected by the Governor and routed to a bounded
  repair/replan decision instead of silently proceeding.
- **Expected result**: Reproduction of R-0.1's Scenario-C-shaped case, but
  through the *normal* (non-fast-path) dispatch route this time: a Worker
  attempting an out-of-declared-scope destructive action on a normal-size
  task is blocked/escalated by Renmark's own contract enforcement, not
  merely by the fast path's narrower guarantee. A second reproduction: an
  Inspector given a failing test cannot itself commit a fix — only a
  separate, logged repair work order can. A third: a task that fails the
  same way twice stops for Owner decision on the third attempt rather than
  silently re-dispatching (this generalizes the repeated-issue-prevention
  guard `renmark/program_driver.py` already has for fast-path reuse — see
  scope note below on what's new vs. reused).

## Scope

### Included

- Worker-scope enforcement (R-0.1's `verify_worker_scope` / `WorkerScope`
  machinery) generalized to non-fast-path dispatch — normal and
  architectural task routing, not just the fast-path classifier's output.
- R-006 Inspectors cannot repair: an explicit, enforced separation between
  an inspection result (PASS/FAIL/finding, no file mutation) and a repair
  action (a distinct, logged work order) — applies to `/renmark:codereview`,
  `/renmark:verify`, and any orchestrate-invoked reviewer role.
- R-008 No speculative agents: every Agent/executor dispatch (fast path or
  not) carries a machine-checkable reason + declared scope + budget
  reservation before it is issued — reusing/extending
  `renmark/subagent_gate.py`'s existing pre-dispatch justification gate
  rather than building a parallel mechanism.
- R-012 bounded rework, generalized: the existing third-equivalent-repair-
  attempt stop (`program_driver.py`, currently exercised via the fast
  path's retry cap per R-0.1/WP-4) applies uniformly across dispatch paths,
  with the same "show ≤5 lines of count/fingerprint evidence + one
  recommendation" contract already documented in CLAUDE.md's
  Repeated-issue-prevention rule.
- Evidence-required replanning per addendum-01 §9.3: a replan (as distinct
  from a same-scope repair) is only permitted when one of the five listed
  triggers is met (Owner requirement change, Inspector architecture-level
  failure evidence, Engineer-proven impossibility, material dependency
  change, material repo drift) and the triggering evidence is recorded, not
  merely asserted.
- R-007 no-nested-delegation, revisited only as a measurement question:
  determine whether any host-independent signal now exists (per
  R-0.1/scope-enforcement-design.md §6 option (b)) to mechanically detect a
  Worker attempting to spawn another agent; if none exists, this item stays
  documented/contractual (same honest-gap posture as R-0.1, not
  re-litigated as a blocker).
- Regression tests proving R-0.1's fast-path behavior and existing
  non-fast-path UX (per R-0.1/WP-3's baseline) are unchanged by generalizing
  scope enforcement to the normal path.

### Excluded

- Phase 3 minimal canonical ledger consolidation — deferred to R-0.3 unless
  this release discovers it's a hard blocker for evidence recording.
- Phase 4 independent/specialized Inspector framework beyond the
  enforce-the-separation change above — full Inspector registry, multiple
  Inspector types, is Phase 4, not this release.
- Phase 5 Planner altitude separation (Architecture mode / Milestone mode)
  — still deferred.
- Phase 8 full Budget Governor (multi-dimension tracking: project/feature/
  milestone/provider/model/context/wall-clock) — this release ships only
  the Phase-2 blocking subset (reason+budget per call), not the full
  governor.
- WritingMate or any remote-provider work — Phase 7, still blocked.
- Building a new nested-dispatch detection mechanism if no
  host-independent signal exists — see scope note above; this release
  investigates and documents, does not invent an unreliable heuristic.

## Engineering acceptance

- A Worker dispatched through the NORMAL (non-fast-path) route with a
  declared scope cannot perform a file operation outside that scope
  without being blocked or triggering explicit escalation — a
  Scenario-C-shaped reproduction through the normal path, not just the
  fast path.
- An Inspector-role finding (review/verify/QA output classified FAIL or
  with findings) never results in a direct file mutation by that same role
  — demonstrated by a reproduction where a reviewer surfaces a defect and a
  SEPARATE, logged work order performs the fix.
- Every Agent/executor dispatch in the covered paths carries a
  machine-checkable reason, scope, and budget reservation prior to
  dispatch — demonstrated by a dispatch attempt missing one of these being
  rejected before any inference call is made.
- A third materially-equivalent repair/replan attempt on the same failure
  stops for Owner decision instead of silently re-dispatching, uniformly
  across fast-path and normal dispatch (not just the fast-path-specific
  case R-0.1 exercised).
- A replan (scope/approach change, not a same-scope repair) is rejected
  unless one of addendum-01 §9.3's five recognized triggers is present with
  recorded evidence.
- R-0.1's fast-path behavior (WorkerScope enforcement, contractual
  no-nested-dispatch) is unchanged — WP-4's baseline plus R-0.1's own
  existing tests still pass.
- Existing non-fast-path command entry points (`/renmark:start`,
  `/renmark:feature`, `/renmark:debug`, `/renmark:orchestrate`) show no
  unintended behavior change outside the newly-enforced boundaries — WP-4's
  regression baseline passes.
- Full existing test suite still passes after implementation.
