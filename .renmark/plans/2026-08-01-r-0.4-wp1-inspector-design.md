# R-0.4 WP-1 — Minimal Inspector Design (role + verdict schema)

Scope: WP-1 only — design and role definition. No ledger code change, no
enforcement check (WP-2), no ledger wiring (WP-3), no call-site wiring
(WP-4), no tests (WP-5). This doc is the input contract for WP-2..WP-4.

## 1. Verdict shape — reuse `InspectionReport`, no new dataclass

R-0.3's `InspectionReport` (`renmark/ledger.py:122-133`) already has the
right shape for a PASS/FAIL/ESCALATE verdict. WP-1 does **not** invent a
parallel schema. The Inspector's verdict populates these existing fields:

| `InspectionReport` field | Type | How the Inspector populates it |
|---|---|---|
| `subject_ref` | `str` | Set to the `order_id` of the `WorkOrder`/`WorkResult` pair under judgment — this is the existing field name that links the verdict back to the work it judges. No new "work_result_ref" field is needed; `WorkOrder.order_id` and `WorkResult.order_id` are already the same value (`WorkResult` carries `order_id`, not its own id), so `subject_ref = work_result.order_id` unambiguously identifies both the order and the result. |
| `verdict` | `str` | One of the literal strings `"pass"` \| `"fail"` \| `"escalate"` (lowercase, matching the existing `"pass"` \| `"fail"` \| `"changes_requested"` precedent style already documented in the dataclass docstring — WP-1 extends the informal enum with `"escalate"`; `validate_inspection_report` only checks `verdict` is a non-empty string today, so this is a documentation-level extension, not a schema break). |
| `findings` | `list[str]` | Cited evidence: file/line refs, test output lines, or contract-clause quotes — one string per citation. Empty `findings` on a `"pass"` verdict is allowed by today's validator (`required=False`... actually `_check_str_list` never requires non-empty) but the WP-1 role prompt (below) directs the Inspector to always cite at least one piece of evidence; enforcing "PASS requires non-empty findings" mechanically, if desired, is a WP-2/WP-3 validator decision, not WP-1's.
| `generator` | `str` | Set to a role marker, e.g. `"inspector"` or `"inspector:<inspector-class-name>"` for future Milestone-5 sub-classing. **`generator` is a role label, not a dispatch-identity signal** — it will be the same string (`"inspector"`) across every Inspector dispatch, so WP-2's independence check must NOT use `generator` to distinguish dispatches. See §2.

`WorkOrder`/`WorkResult` fields the Inspector reads (never writes) as
context, unchanged from R-0.3:
- `WorkOrder.order_id`, `.task`, `.role`, `.file_scope`, `.verifier`
- `WorkResult.order_id`, `.status`, `.summary`, `.touched_files`, `.artifact_refs`

## 2. Dispatch-independence signal (for WP-2 to implement)

**Finding: the current ledger shape has NO field that records "who/what
dispatch produced this event."** `WorkResult` has no identity field at all,
and `InspectionReport.generator` is a role label (e.g. `"inspector"`,
`"code-implementer"`), not a per-dispatch identity — two different
dispatches of the same role produce the same `generator` string, so
`generator` cannot be the mechanical signal WP-2 needs. This is a real gap,
not a naming exercise; WP-2 requires a new field.

### Proposed new field: `dispatch_identity`

Add `dispatch_identity: str = ""` to **both** `WorkResult` and
`InspectionReport` in `renmark/ledger.py`:

```python
@dataclass
class WorkResult:
    order_id: str = ""
    status: str = ""
    summary: str = ""
    touched_files: list[str] = field(default_factory=list)
    artifact_refs: list[str] = field(default_factory=list)
    dispatch_identity: str = ""   # NEW — who/what dispatch produced this result

@dataclass
class InspectionReport:
    subject_ref: str = ""
    verdict: str = ""
    findings: list[str] = field(default_factory=list)
    generator: str = ""
    dispatch_identity: str = ""   # NEW — who/what dispatch produced this verdict
```

- **Value shape**: a string unique per *invocation*, not per role — e.g.
  `"{role}:{session_id}:{dispatch_seq}"` (Renmark already has a session id
  and a monotonic dispatch/task index available at every subagent call site
  per `renmark/dispatch.py`'s dispatch-packet construction and
  `pipeline.json`'s wave/task indices — WP-2 should reuse whichever counter
  already exists there rather than minting a second one). The exact
  composition is WP-2's call, but the **contract WP-1 is fixing** is: this
  string MUST differ between two *separate* dispatch invocations even when
  they share the same `role`, and MUST be stable (identical) within a
  single dispatch's own lifetime (so a Worker's `WorkResult.dispatch_identity`
  and a same-turn self-assessment would collide if one existed — which is
  exactly the self-grading case WP-2 must reject).
- **Mechanical check WP-2 implements**: given a `WorkResult` for
  `order_id = X` with `dispatch_identity = D_worker`, and an incoming
  `InspectionReport` with `subject_ref = X` and `dispatch_identity =
  D_inspector`, reject (raise, do not silently accept) if
  `D_inspector == D_worker` (or if `D_inspector` is empty — an unset
  identity cannot prove independence). This is the "mechanical,
  non-prompt-only signal" the contract's WP-1 acceptance criterion requires
  WP-1 to name: **it is the equality comparison of the two
  `dispatch_identity` string fields**, not any inspection of prompt text or
  role-name string.
- **Validator impact (for WP-2/WP-3 to implement, not WP-1)**:
  `validate_work_result` and `validate_inspection_report` should each grow
  a `_check_str(data, "dispatch_identity", required=False)` line so a
  present-but-wrong-typed value fails loud, matching the existing
  fail-loud-on-write discipline in `append_ledger_event`. Whether
  `dispatch_identity` becomes *required* (non-empty) at write time for
  `InspectionReport` specifically (since an empty inspector identity can
  never prove independence) is a WP-2 decision — WP-1 only flags that the
  field must exist and that emptiness on the *inspector* side should be
  treated as "independence unproven," not "independence assumed."

### Explicitly out of scope for WP-1

- Writing the `dispatch_identity` field into `renmark/ledger.py` (code
  change happens in WP-2/WP-3, per the contract's constraint on this task).
- Deciding the exact string format/algorithm for minting
  `dispatch_identity` values at real call sites (WP-4's job, informed by
  whatever session/dispatch id infrastructure `renmark/dispatch.py` and
  `pipeline.json` already expose).
- Building the rejection path itself (WP-2).

## 3. Role definition

See `plugin/agents/inspector.md` (sibling file, this WP). Mirrors
`plugin/agents/reviewer.md`'s read-only tool restriction (`Read, Grep,
Glob, Bash` — no `Write`/`Edit`). The Inspector role in this file:
reads a `WorkOrder` + `WorkResult` (and, if present, prior `Escalation`
events for the same `order_id`) from the ledger, judges the work, and
returns a structured PASS/FAIL/ESCALATE verdict with cited evidence in its
`SubagentOutput` response. It does **not** call `append_ledger_event`
itself — per this contract's WP-3/WP-4 split, the ledger write happens at
the calling skill's call site, not inside the agent definition.
